MCP from first principles

How I’d explain MCP to an engineer who already understands APIs.

MCP is not magic, and it is not a replacement for your product API. It is a standard way for agent hosts to discover tools, understand their schemas, ask for user consent, and call those tools over a predictable protocol.

0. The shortest useful definition

MCP, the Model Context Protocol, is a protocol for connecting an AI client to external context and capabilities. In ordinary engineering language: it lets an agent ask, “what can I do here?”, receive a list of typed operations, and then call those operations through a standard message format.

The important word is protocol. MCP is not “the database,” “the auth system,” or “the deployment service.” It is the agreement between an agent host and a tool server about how to initialize a session, negotiate capabilities, list tools, call tools, and return results.

For the artifact host, the underlying product capability is still simple: publish HTML artifacts, list versions, update visibility, fetch metadata, and maybe create share links. MCP is one nice way to expose those capabilities to agents.

1. First separate the actors

MCP conversations get confusing when “client,” “server,” “host,” “model,” and “tool” are blended together. Keep the actors separate:

UserThe human asking for work to be done.
Agent hostThe application running the agent experience, such as a coding assistant or desktop app.
MCP clientThe protocol component inside the host that talks MCP.
MCP serverThe process or hosted service that exposes tools, resources, and prompts.
ToolA callable operation, such as publish_artifact or list_artifacts.
Product APIThe normal backend API that actually performs durable product work.

In our product, the MCP server should not contain all business logic. It should be a well-behaved adapter over the same artifact publishing core used by the CLI and REST API.

2. MCP messages are JSON-RPC messages

The wire format is JSON-RPC. That means the protocol has requests, responses, and notifications. A request has an id, a method, and optional params. A response uses the same id so the caller can match it to the request. A notification has no id because nobody is expected to answer it.

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "publish_artifact",
    "arguments": {
      "path": "./dist",
      "slug": "weekend-trip-map",
      "visibility": "private-link"
    }
  }
}

This is the first demystifying point: MCP is not a model-specific incantation. It is structured messages moving between a client and server. The agent host decides when to call a tool; MCP defines how that call is represented.

3. The lifecycle is initialize, operate, shut down

An MCP session has a lifecycle. The client starts by sending initialize. The server answers with the protocol version it supports, the capabilities it offers, and implementation information. Then the client sends an initialized notification. After that, normal work begins.

1. client -> server: initialize
2. server -> client: initialize result
3. client -> server: initialized notification
4. client -> server: tools/list
5. client -> server: tools/call

This handshake matters because MCP is intentionally modular. A server can support tools without resources. Another can support resources without prompts. Another can support logging, completion, or notifications. The initialization phase is where both sides agree on what is actually available.

Think “device enumeration,” not “random HTTP docs”

If you come from systems work, MCP feels a little like enumerating a device or negotiating protocol features. The host asks what the server supports. The server describes capabilities. The host only uses what was negotiated.

4. Tools are the part people usually mean by “MCP”

MCP servers can expose several kinds of things, but tools are the most agent-action-shaped. A tool has a name, a description, and an input schema. The host can show those tools to the model and, depending on its safety policy, allow the model to request calls.

{
  "name": "publish_artifact",
  "title": "Publish HTML artifact",
  "description": "Package and publish a single-page HTML artifact.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": { "type": "string" },
      "slug": { "type": "string" },
      "visibility": {
        "type": "string",
        "enum": ["private", "private-link", "unlisted", "public"]
      }
    },
    "required": ["path", "slug"]
  }
}

That schema is the big product-design win. A generic agent does not need to scrape your docs and guess the shape of an HTTP request. It can ask the MCP server for the available tools, read the schema, fill arguments, and let the host mediate execution.

5. Resources and prompts are different from tools

Tools do things. Resources expose context. Prompts expose reusable prompt templates. You do not need all three on day one, but it helps to know why they exist.

ToolsCallable operations. Publish, delete, list, create share link, render preview.
ResourcesReadable context. Artifact metadata, deployment logs, manifests, profile feed entries.
PromptsReusable workflows. “Turn this folder into a polished artifact manifest.”
Client featuresCapabilities the host can provide back to the server, such as roots, sampling, or elicitation.

For the first artifact MCP server, I would start with tools and maybe a small set of resources. Prompts can come later once the product has repeated workflows worth packaging.

6. stdio MCP means “the host launches a local process”

In stdio transport, the agent host starts the MCP server as a child process. The host writes JSON-RPC messages to the server’s standard input. The server writes JSON-RPC messages to standard output. Logs go to standard error. That last detail matters: stdout is protocol traffic, so printing random logs to stdout can break the connection.

Agent host
  launches
    artifact-mcp --stdio

Host stdin  -> server receives JSON-RPC
Server stdout -> host receives JSON-RPC
Server stderr -> logs/debug output

The useful intuition: stdio MCP is local, simple, and excellent for tools that need local filesystem access. If the user asks an agent to publish ./dist, a local MCP server can read that folder, validate files, package assets, and call the artifact API.

The security boundary is also local. The user installed or configured the server. The host launches it. Credentials should come from the local environment, config file, OS keychain, or the same auth store the CLI uses. This is why the MCP spec says HTTP auth rules are for HTTP transports, while stdio implementations should retrieve credentials from the environment or a custom strategy.

7. Remote MCP means “the server is a hosted network service”

Remote MCP uses Streamable HTTP. The MCP server runs as an independent service, potentially serving many users and many clients. The client sends JSON-RPC messages with HTTP POST to a single MCP endpoint, such as https://artifact.example.com/mcp. The server can return ordinary JSON, or use Server-Sent Events when it needs streaming, notifications, or resumability.

Hosted agent client
  POST /mcp       -> JSON-RPC request
  GET /mcp        -> optional SSE stream
  MCP-Session-Id  -> optional stateful session handle
  Authorization   -> OAuth access token for protected servers

Remote MCP is the right fit when the agent client is itself hosted, when the tool does not need local files, or when you want a service users can connect without installing a local binary. It also brings the normal problems of hosted software: authentication, tenant isolation, rate limits, logs, abuse prevention, and upgrade compatibility.

For the artifact host, remote MCP might eventually expose account-level operations: list artifacts, inspect deployment status, generate private links, change visibility, or publish from a fetched bundle. But anything that starts with “read my local folder” is naturally a local stdio job.

8. stdio vs remote is mostly about where the trust boundary lives

stdioLocal child process. Great for filesystem access, local credentials, and developer workflows.
RemoteHosted HTTP service. Great for cloud access, multi-client connectivity, and no-install onboarding.
stdio authUsually config, environment, OS keychain, or CLI login state.
Remote authUsually OAuth-style authorization and access tokens.
stdio scalingOne local process per configured host/user environment.
Remote scalingShared service concerns: sessions, tenants, observability, rate limits.

A useful rule: if the tool needs local machine affordances, start stdio. If the tool is a cloud account integration that many agent hosts should connect to directly, design remote MCP.

9. What should this product build first?

For the agent-native artifact host, I would build in this order:

  1. REST API: the durable product contract for publishing, versions, metadata, and visibility.
  2. Shared core package: packaging, manifest validation, file walking, hashing, upload planning, and API client logic.
  3. CLI: a human-operable shell around the core package.
  4. Local stdio MCP: an agent-operable shell around the same core package.
  5. Remote MCP: later, once hosted agents need delegated account access without local installation.
artifact-core
  packageArtifact()
  validateManifest()
  createUploadPlan()
  callArtifactApi()

artifact-cli
  artifact publish ./dist

artifact-mcp-stdio
  publish_artifact({ path: "./dist", slug: "trip-map" })

artifact-worker-api
  POST /api/artifacts
  POST /api/artifacts/:id/versions

This avoids the trap of building three products. CLI and MCP should be thin interfaces over the same implementation. The REST API remains the source of durable server behavior.

10. Why not just give the agent a REST API?

You should have a REST API. The question is whether REST alone is the right interface for agents.

REST is a backend contract. It is excellent for stable product operations. But an agent needs more than an endpoint URL. It needs to discover what operations exist, understand argument schemas, know which calls are dangerous, receive user-mediated credentials, stream progress, and fit into the host’s tool approval UI.

REST APIBest as the canonical product backend. Durable, testable, language-neutral, good for web apps and SDKs.
CLIBest for humans and scripts. Great ergonomics, local file access, terminal output, CI usage, and debugging.
MCPBest for agent hosts. Discovery, typed tool schemas, capability negotiation, consent surfaces, and cross-client interoperability.
SDKBest for application developers embedding the product into their own codebases.

If you only provide REST, every agent integration has to rediscover your API shape from docs or examples. It has to decide how to authenticate, which endpoints correspond to user intent, which arguments are required, and whether the action needs confirmation. That can work, but it is brittle.

MCP turns “please read our docs and improvise an HTTP call” into “here are the tools this server exposes, here are the schemas, here is the negotiated session, here is the host-mediated call path.” The agent still may call a REST API under the hood; it just does so through a safer, more inspectable tool layer.

11. Why have CLI and MCP?

CLI and MCP overlap, but they serve different operators.

The CLI is for a person at a terminal, a shell script, or CI. It should have good help text, readable errors, login/logout commands, and composable flags. If something goes wrong, the user can run it again, inspect files, pass --verbose, or pipe output somewhere.

MCP is for an agent host. Its job is to make the operation legible to the model and the host: available tools, argument schemas, tool descriptions, safety metadata, progress, and structured results. A person may never type the tool call directly.

The product answer

Build one publishing engine, then expose it three ways: REST for the backend contract, CLI for humans and automation, MCP for agents. Do not fork the business logic.

12. The deployment shape I would use

For day one, ship a local stdio MCP server with the CLI package:

npm install -g artifact

artifact login

# agent host config points to:
artifact mcp --stdio

That server uses the same local auth state as the CLI. The agent can publish local folders because the process runs on the user’s machine. The hosted Worker API still performs server-side authorization and storage.

Later, ship a remote MCP endpoint:

https://artifact.example.com/mcp

That endpoint uses Streamable HTTP, OAuth authorization, strict origin checks, tenant-aware logging, rate limits, and explicit scopes such as artifact:read and artifact:write. It is useful for hosted agent platforms and account-level operations, but it should not replace the local path for local file publishing.

13. The mental model to keep

MCP is a tool bus for agents. REST is your product API. The CLI is your human and automation interface. The clean architecture is not choosing one; it is making sure each interface is a thin layer over the same core capabilities.

For this product, the primitives become nicely aligned:

  1. The user or agent creates HTML.
  2. The shared core validates and packages it.
  3. The CLI or MCP server submits it to the REST API.
  4. The Worker authorizes the request and stores the artifact.
  5. The profile/feed/card surfaces make the artifact visible.

That is the whole idea: agents are excellent at generating useful little pieces of software. MCP gives those agents a clean, typed, host-aware way to hand those pieces to the publishing system.
