Auth from first principles

How I’d explain auth to a junior engineer building an agent-native HTML host.

Start with the browser. Then add sessions. Then add tools. Only after that do OAuth, OIDC, PKCE, and MCP start to feel like reasonable answers instead of a bag of acronyms.

0. The whole problem in one sentence

Authentication systems answer two questions over and over: who is making this request? and what are they allowed to do?

For the artifact-hosting product, the callers are not only humans in browsers. They are also CLIs, local MCP servers, hosted agent platforms, and people opening private share links. The mistake would be to use one credential shape for all of them. A browser session is excellent for the dashboard. A deploy token is better for a CLI. A share token is useful for private links. OAuth is the right tool when some other app needs delegated access on behalf of a user.

1. Cookies: the browser’s memory for a site

A cookie is a small piece of data a server asks the browser to store. The important part is not that it is small. The important part is that the browser automatically sends matching cookies back to the same site on later requests.

Suppose the server responds with this:

HTTP/1.1 200 OK
Set-Cookie: session=sess_9pL...; HttpOnly; Secure; SameSite=Lax

The browser stores the cookie. Later, when the browser requests the dashboard, it sends:

GET /dashboard
Host: example.com
Cookie: session=sess_9pL...

Your JavaScript did not manually attach that cookie. The browser did it because the request matched the cookie’s rules.

What is actually in the cookie?

For login, usually a random session ID. Not the user’s whole profile. Not their password. Not “user_id=123” if you can avoid it. The cookie should be an opaque, high-entropy secret that the server can look up.

Cookies have attributes that decide when they are sent and how exposed they are:

DomainWhich host receives it. A host-only cookie is narrower than one shared across subdomains.
PathWhich URL paths receive it. A cookie scoped to /dashboard is not sent everywhere.
Expires / Max-AgeHow long it lasts. Without this, it is usually a session cookie.
HttpOnlyJavaScript cannot read it. This helps if a page has an XSS bug.
SecureOnly sent over HTTPS. Auth cookies should always use this.
SameSiteControls cross-site sending. This is one major CSRF defense.

The superpower of cookies is also the danger: they are automatic. If you are logged into a site, and another site tricks your browser into submitting a form to it, the browser may include your cookies. That attack is called CSRF, cross-site request forgery. SameSite cookies help. CSRF tokens help. But the root intuition is simple: cookie auth rides along with browser requests automatically, so write endpoints need extra care.

2. A session is the server-side meaning of a cookie

A cookie by itself is just a value. A session is what your server thinks that value means.

A simple session table might look like this:

sessions
  id_hash
  user_id
  created_at
  expires_at
  revoked_at

When the browser sends session=sess_9pL..., the Worker hashes the raw session value, looks for that hash in D1, checks expiration and revocation, and loads the user. The server stores the hash instead of the raw secret for the same reason password databases store password hashes: if the database leaks, you do not want attackers to get immediately usable session cookies.

Once the request has a user, you still have to check authorization. “This is Akshay” is not the same as “Akshay can edit this artifact.” That second question is a permission check.

3. Authentication is identity. Authorization is permission.

These words are annoyingly similar, but the distinction matters constantly.

AuthenticationWho is making the request? A logged-in user, a CLI token, a hosted agent, a private-link viewer?
AuthorizationWhat may that caller do? Publish, read, change visibility, rollback, delete, invite?
CredentialWhat proof did the caller present? A cookie, bearer token, share token, or OAuth access token.

For this product, a write request should eventually read like a sentence: “This request is from deploy token tok_123, belonging to Akshay, scoped to artifact:write, attempting to publish to Akshay’s namespace.” Then your authorization code asks whether that sentence is allowed.

4. Non-browser tools should not use browser cookies

A CLI is not a browser. A local MCP server is not a browser. They should not scrape, copy, or reuse the dashboard cookie. Instead, they should use a token designed for API access.

The login flow can still begin in the browser:

  1. The user runs artifact login.
  2. The CLI opens a browser to the normal login page.
  3. The user signs in and approves the device.
  4. The server mints a scoped deploy token.
  5. The CLI stores the raw token in the OS keychain.
  6. The server stores only a hash of the token in D1.

From then on, the CLI publishes like this:

POST /api/deploy
Authorization: Bearer art_live_B7k...

A bearer token is called that because whoever “bears” it can use it. Possession is enough. That is powerful and dangerous. The token needs a name, scopes, expiration, revocation, and ideally a visible “last used” timestamp in the dashboard.

5. Local MCP can reuse the CLI’s trust model

The first MCP server should be local over stdio. That means it runs on the user’s machine, launched by Codex, Claude Desktop, or another agent client. This matters because the local MCP server can read local files and package the HTML artifact before upload.

The shape is:

Agent client -> local MCP server -> artifact-core -> hosted Worker API

The local MCP server can reuse the CLI token because it has the same trust boundary: the user installed a local tool and granted it the ability to publish. The shared implementation should live below both shells:

packages/
  artifact-core   # packaging, manifest validation, API client
  artifact-cli    # terminal wrapper
  artifact-mcp    # MCP tool wrapper
  artifact-worker # Cloudflare API

This keeps the mental model clean. CLI and MCP are not two separate auth systems. They are two interfaces to the same publishing core.

6. Private links are bearer tokens in the URL

Private link and unlisted are easy to confuse. They are not the same thing.

PrivateRequires the owner to be logged in.
Private linkRequires possession of a secret share URL.
UnlistedNormal URL works, but it does not appear in profile/search.
PublicNormal URL and discoverable.

Unlisted is about discovery. Private link is about access. A private link might look like /share/sh_8Vq3.... The Worker hashes that share token, checks whether it is valid, and serves the artifact if it is.

Because the token is in the URL, it can leak through screenshots, chat history, browser history, server logs, or referrer headers if you are careless. That does not mean private links are bad. They are incredibly useful. But they are best for “anyone with this link may view,” not “only my spouse may view.” For that, require login and an access control list.

7. OAuth is for delegated access

OAuth is often introduced as “login with Google,” which is a little misleading. OAuth 2.0 is mostly about authorization: letting one application access a resource on behalf of a user without giving that application the user’s password.

The actors are:

Resource ownerThe user. In our product, Akshay.
ClientThe app asking for access, such as a hosted MCP client.
Authorization serverThe service that authenticates the user and issues tokens.
Resource serverThe API receiving the token, such as the artifact Worker API.
ScopeA permission string like artifact:write.
Access tokenThe short-lived credential the client presents to the API.

OpenID Connect, or OIDC, adds identity on top of OAuth. OAuth says “this client may access this thing.” OIDC adds “and here is who the user is.” That is where ID tokens and profile claims come from.

8. PKCE is the proof that protects the code exchange

The modern OAuth flow for public clients is Authorization Code with PKCE. “Public client” means a client that cannot safely keep a secret. A native app, browser app, CLI, or agent client cannot hide a client secret from the environment it runs in.

PKCE stands for Proof Key for Code Exchange, pronounced “pixy.” It protects against an attacker stealing the temporary authorization code and redeeming it first.

  1. The client creates a random code_verifier.
  2. It sends a derived code_challenge when starting the login flow.
  3. The user approves access.
  4. The authorization server returns a short-lived authorization code.
  5. The client exchanges the code plus the original code_verifier.
  6. The server checks that the verifier matches the earlier challenge.
  7. If it matches, the server returns tokens.

The key idea: the authorization code is not enough. The client must also prove it is the same client that started the flow.

9. Remote MCP is where OAuth becomes necessary

A local MCP server can use the CLI token because it runs on the user’s machine. A remote MCP server is different. It may serve many users, run outside the user’s machine, and be invoked by hosted agent clients. That is delegated access, so OAuth is the right family of tools.

A reasonable later architecture looks like this:

  1. The hosted agent client asks to connect the artifact MCP server.
  2. The user is redirected to the artifact host’s authorization page.
  3. The user approves scopes like artifact:read and artifact:write.
  4. The client receives an access token through Authorization Code + PKCE.
  5. The remote MCP calls the artifact API with that access token.
  6. The API validates issuer, audience, expiration, and scopes before doing anything.

This is not necessary for the first local MCP. It is the correct shape once hosted agents need to act on behalf of users.

10. Token jobs: do not mix these up

        

          
Session cookieBrowser login state. HttpOnly, Secure, SameSite.

          
Bearer tokenWhoever holds it can use it. Sent in the Authorization header.

          
Deploy tokenA bearer token for CLI/local MCP publishing. Store only a hash server-side.

          
Access tokenA usually short-lived OAuth API token with audience and scopes.

          
ID tokenOIDC identity claims for the client. Not usually your API authorization primitive.

          
Refresh tokenUsed to get new access tokens. High value; rotate and protect carefully.

        

      


      

        
11. Threat modeling makes the design concrete

        
Auth starts to click when you stop asking “is this secure?” and start asking “what happens if this exact credential leaks?”

        

          
Session cookie leaksAttacker may act as the user in the browser session. Use HttpOnly, Secure, SameSite, short expiry, rotation, and logout revocation.

          
Deploy token leaksAttacker may publish or read artifacts within its scopes. Store only token hashes, support revocation, expiration, and least-privilege scopes.

          
Share token leaksAnyone with the link can view that private-link artifact. Make links unguessable, artifact-specific, revocable, and optionally expiring.

          
Access token leaksAttacker can call the API until expiry. Keep access tokens short-lived and audience-scoped; rotate refresh tokens if used.

        

      


      

        
12. Why is it called that?

        
Names are memory hooks. These are the ones that matter for this product:

        

          
S3Amazon Simple Storage Service. Three S words, hence S3. Store objects in buckets and retrieve them by key.

          
R2Cloudflare's object store. Cloudflare's launch post says R2 means “Really Requestable,” plus a few playful alternates; the product is S3-compatible storage without egress fees.

          
D1Cloudflare's first SQL database for Workers. The name reads like Database One / D1, though the docs do not lean heavily on an acronym.

          
OAuthOpen Authorization. It is about delegated access.

          
OIDCOpenID Connect. It connects identity/login semantics to OAuth-style flows.

          
PKCEProof Key for Code Exchange. It proves the app exchanging the code is the same one that started the flow.

          
Bearer tokenWhoever bears/presents the token can use it.

          
CookieAn old web term for a small piece of data a server asks the browser to store and send back later.

          
CSRFCross-site request forgery. A different site tries to make your browser send an authenticated request.
