The mental model

        
Authentication answers who you are. Authorization answers what you can do.

      

      

        

          Authentication
          
Identify the caller

          
Is this Akshay in the browser? Is this Akshay's laptop using a deploy token? Is this a viewer holding a private share link?

        

        

          Authorization
          
Check permission

          
Can this caller publish to this namespace? Can they read this private artifact? Can they change visibility?

        

        

          Credential
          
Proof presented

          
A browser cookie, bearer token, share token, or OAuth access token. Each is just a different kind of proof.

        

      

    


    

      

        
Recommended path

        
Learn auth as a sequence of trust decisions.

        
Do not start with OAuth. Start with one browser request. Then ask: what proof did the caller present, where did that proof come from, how can it be stolen, and what is the caller allowed to do?

      

      

        
1Session cookie: how a browser stays logged in.

        
2Bearer token: how a non-browser tool calls an API.

        
3Scopes and ACLs: how authorization is checked.

        
4OAuth + OIDC: how another app gets delegated access and identity.

        
5MCP: which auth style fits local vs hosted agent tools.

      

    


    

      

        
OAuth, precisely

        
OAuth is usually about delegated authorization, not login by itself.

        
OAuth lets one client access a resource on behalf of a user without receiving the user's password. OpenID Connect, or OIDC, layers identity on top of OAuth so the app can also learn who signed in.

        
For this product, OAuth matters most for remote MCP later. The local CLI can use a simpler browser-login-to-deploy-token flow first.

      

      

        
OAuth 2.0Delegated access: issue access tokens with scopes.

        
OIDCIdentity layer: adds ID tokens and user profile claims.

        
PKCEProof key: protects public clients that cannot keep a client secret.

        
ScopesPermission strings like artifact:write or artifact:read.

      

    


    

      

        
Why is it called that?

        
Name origins make the map easier to remember.

      

      

        
S3Amazon Simple Storage Service. Three S words, hence S3. Store objects in buckets and retrieve them by key.

        
R2Cloudflare's object store. Cloudflare's launch post says R2 means “Really Requestable,” plus a few playful alternates; the product is S3-compatible storage without egress fees.

        
D1Cloudflare's first SQL database for Workers. Cloudflare describes it as their first SQL database; the name reads like Database One / D1, though the docs do not lean heavily on an acronym.

        
OAuthOpen Authorization. It is about delegated access: one app is authorized to access something on your behalf.

        
OIDCOpenID Connect. It connects identity/login semantics to OAuth-style flows.

        
PKCEProof Key for Code Exchange. Pronounced “pixy.” It proves the app exchanging the code is the same one that started the flow.

        
Bearer tokenWhoever bears/presents the token can use it. That is why bearer tokens must be protected.

        
CookieAn old web term for a small piece of data a server asks the browser to store and send back later.

        
CSRFCross-site request forgery. A different site tries to make your browser send an authenticated request.

      

    


    

      

        
Authorization code + PKCE

        
The modern OAuth flow is a two-step exchange with a proof key.

      

      

        
1Client creates code_verifier
A random secret stays in the client.

        
2Client sends code_challenge
The user is redirected to authorize access.

        
3Authorization server returns code
The code is temporary and not enough by itself.

        
4Client exchanges code + verifier
The server checks the verifier matches the challenge.

        
5Server returns tokens
Usually an access token, sometimes refresh and ID tokens.

      

    


    

      

        
Tokens

        
Most auth bugs come from mixing up token jobs.

        
A session cookie is for the browser. A deploy token is for the CLI or local MCP. An access token is for an API call. An ID token proves identity to the client. A refresh token gets new access tokens and should be handled carefully.

      

      

        
Session cookieBrowser login state. HttpOnly, Secure, SameSite.

        
Bearer tokenWhoever holds it can use it. Send in Authorization header.

        
Deploy tokenLonger-lived API token for CLI/local MCP. Store hash server-side.

        
Access tokenShort-lived API authorization token, often scoped.

        
ID tokenOIDC identity claims. Meant for the client, not usually your API auth.

        
Refresh tokenUsed to obtain new access tokens. High value, rotate and protect.

      

    


    

      

        
Threat model

        
Each credential has a different failure mode.

        
Auth starts to click when you stop asking “is this secure?” and start asking “what happens if this exact credential leaks?”

      

      

        
Session cookie leaksAttacker may act as the user in the browser session. Use HttpOnly, Secure, SameSite, short expiry, rotation, and logout revocation.

        
Deploy token leaksAttacker may publish or read artifacts within its scopes. Store only token hashes, support revocation, expiration, and least-privilege scopes.

        
Share token leaksAnyone with the link can view that private-link artifact. Make links unguessable, artifact-specific, revocable, and optionally expiring.

        
Access token leaksAttacker can call the API until expiry. Keep access tokens short-lived and audience-scoped; rotate refresh tokens if used.

      

    


    

      

        
Visibility

        
Private link and unlisted are not the same thing.

        
Unlisted is about discovery. Private link is about access. If the content is sensitive, use private or private link. If it is merely not meant for the profile feed, unlisted is fine.

      

      

        
PrivateOwner session required.

        
Private linkSecret share URL grants view access and can be revoked.

        
UnlistedNormal URL works, but the artifact is hidden from profile/search.

        
PublicNormal URL and visible on profile/feed/discovery.

      

    


    

      

        
The MVP design

        
Keep the first version boring on purpose.

      

      

        

          1
          
Human signs in

          
Magic link or OAuth creates a web session cookie for the dashboard.

        

        

          2
          
CLI logs in once

          
The CLI opens the browser, receives a scoped deploy token, and stores it in the OS keychain.

        

        

          3
          
Local MCP reuses it

          
The stdio MCP server runs locally, reads files, packages HTML, and calls the API with the same token.

        

        

          4
          
Remote MCP waits

          
Hosted agents need OAuth and consent screens. That is real but not necessary for day one.

        

      

    


    

      

        
Jargon map

        
The vocabulary you will see in real systems.

      

      

        
PrincipalThe actor: user, service account, agent, or share-link holder.

        
SubjectThe identity the system says the principal has, often a user ID.

        
ClaimA fact inside a token, like email, issuer, audience, or expiration.

        
IssuerThe auth server that minted a token.

        
AudienceThe API or service the token is intended for.

        
ScopeA coarse permission string attached to a token.

        
CSRFCross-site request forgery. Mostly a cookie-auth concern.

        
CORSBrowser rule controlling which origins can read responses.

        
JWK / JWKSPublic keys used to verify signed JWTs.

        
IntrospectionAsking the auth server whether an opaque token is valid.

        
RevocationInvalidating a token or session before it expires.

        
Least privilegeGive a token only the permissions it needs.
